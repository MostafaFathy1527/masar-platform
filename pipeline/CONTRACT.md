# Content pipeline — generation contract

Rules for generating lesson content in this repository. They exist because the same
mistakes recur, and because a generator that is trusted rather than checked produces work
nobody can defend.

## The order that matters

The gates were built **before** the generation. `validate.py`, `concept_log.py` and
`qa_gate.py` all existed, ran in CI, and had negative tests proving they refuse things,
before a single lesson was generated by this pipeline.

That ordering is the argument. A generator built first and gated later is gated to
whatever it already produces; gates built first define what is acceptable independently of
what any model happens to emit.

## What the pipeline may and may not do

**May:** draft lesson JSON and item JSON from a source note, at a requested level.

**May not:**
- **Publish.** Output arrives as `status: DRAFT`. A human clicks publish. This is a
  permission boundary, not a convention.
- **Invent facts about insurance practice.** If a claim is not in the source note, it goes
  to `needs-verification.md` for a human to confirm or cut. A plausible sentence nobody
  can source is the most expensive kind of output.
- **Read anything outside `pipeline/sources/`.** No client material, no employer material,
  no scraping.
- **Edit a previous output in place.** Copy to `vN+1`. If a human hand-edited an output,
  **their version is the new baseline** and regeneration diffs onto it.

## Hard content rules

1. **No real licensed code sets.** No CPT, HCPCS, CDT, DRG, or X12 remark and adjustment
   code shapes. Every code is a fictional training code: `PRC-1000` family for procedures,
   `DX-A100` for diagnoses. `validate.py` enforces this and an occurrence is an automatic
   rubric 1.
2. **No employer or client names**, ever, in any form. The denylist is untracked and
   passed to `validate.py --denylist`.
3. **Fictional payers, clinics, patients and amounts**, labelled as training data.
4. **Every option carries feedback naming the misconception it represents.** A distractor
   without one is a QA failure, not a stylistic preference.
5. **≤180 words of prose between two acting blocks at L2+.** Checked mechanically.
6. **Arabic is not optional on a lesson that claims to be bilingual.** If a lesson ships
   English-only, set `bilingual: false` — the player then says so on the page. Pasting
   English into Arabic fields while claiming Arabic is caught by both gates.

## The loop

```
source note  →  generate  →  validate.py  →  concept_log.py  →  judge  →  qa_gate.py
                    ↑                                                          │
                    └──────────── one retry with the report appended ──────────┘
                                                                    then stop for a human
```

Each gate is a hard fail. They are ordered cheapest-first on purpose: there is no point
paying for a judgement on a document that does not parse.

The judge step can be run more than once with different models (`judge_bedrock.py` writes
`verdict.<tag>.json` beside the lesson), and `compare_verdicts.py` reports how far they
disagree. Every verdict still goes through `qa_gate.py`; the thresholds do not move.
No model call sits in any request path. The judges run by hand, and every week in
`.github/workflows/judge-panel.yml`, which reaches Bedrock through GitHub OIDC (no stored key)
and rents the open seat's GPU with a repository secret; no credential is kept in the
repository. A judge is either a Bedrock model or an open model served on your own or rented
hardware behind an OpenAI-compatible endpoint (`--endpoint`); the prompt, the
parsing and the gate are the same for both, and the verdict records which it was.

A verdict whose scores, notes and closing note all equal the example printed in the rubric is
refused like unparseable output: the judge handed the example back instead of reading the
lesson (what-failed entry 19). `kaggle_open_judges.ipynb` runs the calibration on open models
served by llama.cpp on Kaggle's free GPUs.

`panel.py` turns several verdicts into one decision: PASS only if every seat has scored, every
judge passes and no criterion splits them by more than one point; a split, a disagreement on
the outcome or an empty seat is NEEDS HUMAN, not an average. The latest verdict per model
counts. One judge is refused. The panel has four seats: three hosted on Bedrock (Kimi K3,
DeepSeek V3.2, GLM-5) and, since 18 October, one open judge, Qwen3-30B-A3B-Thinking-2507,
served by llama.cpp behind the endpoint in `JUDGE_QWEN3_ENDPOINT`.

A judge earns a panel seat by passing `calibrate_judges.py`: given a lesson's real items and
copies broken in ways rubric criterion 4 names, it must score the broken copies at least two
points lower. The first panel failed this and was retired (what-failed entry 18). Every judge
sees the items behind the lesson's knowledge checks, and refuses to run if one is missing.
The seated panel is calibrated on knowledge checks and worked examples, and two of its
judges, GLM-5 and Kimi K3, also on English pasted into Arabic fields: each caught 4 of 4 where
DeepSeek V3.2 caught 1 and Qwen3 caught 2 (1 on its second pass), so that defect splits the
panel and goes to a person. No judge tested is calibrated on scenario consequences: of every
judge tried, hosted and open, Kimi K3 came closest, catching three of four.
Kimi K3 replaced Kimi K2.5 on 15 October; it runs at its own default temperature, and its
verdicts record that. Both defects are also refused by `validate.py`, and a person reads
scenarios.

`run_lesson.py` runs the whole loop with one command: generate from a source note, the
mechanical gates (including an item-bank check that mirrors `lib/schema/item.ts`), the
panel, and the single retry, then stops. It refuses a generator from any model family that
sits on the panel, so no judge scores its own family's work. Each run keeps `run.json` and
`run-report.md` beside its versions; no person edits anything between the note and the
report, and the result is still a DRAFT.

## Known failure modes

Recorded because they recur, and because a pipeline that does not write these down repeats
them:

- **Definition drift.** A later lesson re-explains a concept an earlier one taught. The
  learner assumes they missed something. `concept_log.py` refuses it.
- **Forward reference.** A lesson leans on a term introduced later. Same check.
- **Cards that are lists.** A "visual card" containing three bullets is a list wearing a
  border. Rubric criterion 2.
- **Distractors nobody would pick.** They make an item easier while looking thorough.
  Rubric criterion 4.
- **Feedback that restates the stem.** "Correct, because this is the correct answer."
  Rubric criterion 4.
- **Confident invention.** Fluent, plausible, unsourced. Goes to `needs-verification.md`.
- **Position bias.** Authoring the correct option first in every item. Found in this
  project by playing the bank adversarially: "always answer A" scored 89%. Options are
  shuffled per attempt at serve time, so authored order is not load-bearing — but do not
  rely on that to excuse a keyed bank.

## Files

```
pipeline/
  CONTRACT.md            this contract
  rubric.md              8 criteria, the thresholds, and what the score is worth
  prompts/               generate · revise · judge
  sources/               the only permitted input
  memory/
    concept-log.json     what has been taught, and where
    run-log.jsonl        every run, including failures
  validate.py            structure, semantics, forbidden content
  concept_log.py         re-definition and forward-reference checks
  qa_gate.py             applies the rubric thresholds, writes the report
  judge_bedrock.py       one judge, one lesson: the rubric in a fresh context; scores every
                         panel seat (Bedrock, or an open model behind an OpenAI-compatible endpoint)
  compare_verdicts.py    criterion-by-criterion agreement between two or more verdicts
  panel.py               several judges, one decision; any split goes to a human
  served_judge_vm.py     rents the open seat's GPU machine for a run, and terminates it
  served_judge_setup.sh  on that machine: builds llama.cpp, serves the seated file if its sha256 matches
  run_lesson.py          the loop end to end: source note to judged draft, one retry
  calibrate_judges.py    planted defects: which judges can tell real items from broken ones
  kaggle_open_judges.ipynb  the same calibration for open models on Kaggle's free GPUs
  test_*.py              negative tests for each gate
```
